# Участие в разработке документации

## Подготовка

Прочитайте [принципы](docs/guide/principles.md), [словарь](docs/guide/terms.md) и [правила проверки](docs/guide/quality.md). Установите зависимости по [README](README.md).

## Ветка и изменения

1. Обновите локальную `main`: `git switch main`, затем `git pull --ff-only`.
2. Создайте ветку: `git switch -c docs/название-раздела`. Для машинных имён используйте латиницу, например `docs/accessibility`.
3. Добавьте файл в `docs/guide/` и пункт в `nav` файла `mkdocs.yml`.
4. Для нового правила задайте идентификатор, требование, пример и способ проверки.
5. Проверьте факты по закреплённой версии backend. Не выдавайте планы продукта за реализованные функции.
6. Запустите проверки, перечисленные ниже, и просмотрите сайт через `mkdocs serve`.
7. Создайте коммит, отправьте ветку и откройте Pull Request в `main`.

```bash
python -m pymarkdown --config .pymarkdown.json scan --recurse README.md CONTRIBUTING.md docs
mkdocs build --strict
git add docs mkdocs.yml
git commit -m "docs: add documentation section"
git push -u origin HEAD
```

## Содержание Pull Request

Укажите проблему читателя, изменённые страницы, источники фактов, выполненные проверки и исключения из правил. Для примера «до/после» объясните, какие нарушения устранены.

В разделе Reviewers GitHub выберите реального другого студента, если у него есть доступ к репозиторию. Если его учётная запись неизвестна, передайте ему ссылку самостоятельно. Не создавайте фиктивное ревью и не одобряйте собственный PR от чужого имени.

## Ревью и слияние

Рецензент проверяет точность, понятность, навигацию и примеры; CI проверяет формат и сборку. Исправьте замечания отдельным коммитом и повторно запросите ревью. Владелец сливает PR только после успешного CI и реального одобрения другого студента. Если одобрение отсутствует, PR остаётся открытым.

Для технической защиты этого процесса владелец может включить правило защиты `main`: один approval и обязательный check `check`. Доступность этой настройки зависит от тарифа GitHub; текстовое правило само по себе не является серверной блокировкой.

## Поддержка

При изменении API обновляйте словарь, примеры и ссылки в том же PR. Владелец стайлгайда — Фёдор Марков. Пересмотр правил — при изменении продукта и перед сдачей лабораторной. Исключение описывайте в PR: правило, причина, область действия и решение рецензента.
