# Доступность текста

Эти правила помогают читать документацию с экранным диктором, с клавиатуры, при увеличении страницы и при ограниченном опыте работы с API. Они дополняют правила Markdown и не означают сертификацию сайта на соответствие WCAG.

## Структура и язык

**A-01. Обязательно:** используйте последовательные уровни заголовков и описательные названия. Один `#` обозначает тему страницы; `##` — раздел, `###` — подраздел. Не заменяйте заголовок полужирной строкой.

Плохо: после `# Запуск` сразу `### Ошибки`. Хорошо: `# Запуск` → `## Подготовка` → `## Шаги` → `## Ошибки`.

Проверка: просмотрите оглавление и порядок заголовков. Он должен передавать структуру без чтения всего текста. Основание: [рекомендации W3C WAI по заголовкам](https://www.w3.org/WAI/tutorials/page-structure/headings/).

**A-02. Обязательно:** пишите короткие действия с явным результатом, раскрывайте сокращения при первом использовании, объясняйте термины через словарь. Не сообщайте важное только цветом, расположением или значком.

Плохо: «Нажмите зелёную кнопку справа». Хорошо: «Нажмите **Сохранить**. В списке появится обновлённый статус заказа».

Проверка: инструкция понятна при чтении вслух без вида страницы. Для ошибки укажите текстовый статус и следующее действие, например: «Сборка завершилась с ошибкой. Откройте журнал задания check».

## Ссылки и изображения

**A-03. Обязательно:** текст ссылки описывает цель вне окружающего предложения. Избегайте «здесь», «подробнее» и одиночного URL в качестве единственной подписи.

Плохо: «Для проверки нажмите здесь». Хорошо: «Откройте [протокол проверки стайлгайда](../examples/validation.md)».

Проверка: прочитайте только подписи ссылок страницы; их назначение должно быть различимо. Основание: [W3C WAI: написание доступного текста](https://www.w3.org/WAI/tips/writing/).

**A-04. Обязательно:** информативное изображение имеет альтернативное описание, передающее его назначение. Сложная схема дополнительно объяснена текстом рядом. Декоративное изображение имеет пустое описание; в этой документации декоративные изображения рекомендуется не добавлять.

Плохо: `![alt text](architecture.png)`. Хорошо: `![Основной API и клиент ресторана обращаются к PostgreSQL через backend](architecture.png)` — пример синтаксиса. Для сложной архитектуры отдельно перечислите компоненты и связи в тексте.

Проверка: при отключённых изображениях не теряется информация, необходимая для выполнения задачи. Основание: [W3C WAI: изображения](https://www.w3.org/WAI/tutorials/images/).

## Команды и таблицы

**A-05. Обязательно:** команды и сообщения об ошибках представлены копируемым текстом, а не только скриншотом. У таблиц есть понятные заголовки столбцов. Не используйте таблицы для раскладки страницы; при сложной структуре разбейте таблицу на несколько простых.

Плохо: снимок терминала без текста. Хорошо: блок `bash` и отдельный абзац «Ожидаемый результат: база принимает соединения».

Проверка: выделите и скопируйте команду; прочитайте таблицу построчно. Значение каждой ячейки должно быть понятно по её заголовку. Основание: [W3C WAI: таблицы](https://www.w3.org/WAI/tutorials/tables/).

## Контроль перед публикацией

**A-06. Обязательно:** после изменения страницы выполните ручную проверку и укажите её результат в PR. Если проверка не выполнена, так и напишите.

1. Проверьте порядок заголовков и подписи ссылок.
2. Увеличьте страницу до 200 %: текст должен оставаться читаемым, элементы управления — доступными. Проверьте узкую область просмотра; для длинного кода допустима горизонтальная прокрутка блока.
3. Клавишами Tab, Shift+Tab и Enter проверьте достижимость меню, поиска и ссылок, видимость фокуса и отсутствие ловушки клавиатуры.
4. Проверьте, что смысл примера сохраняется без цвета и изображений.
5. При наличии экранного диктора проверьте заголовки, ссылки и таблицы. Запишите название инструмента и замечания; при его отсутствии не заявляйте эту проверку проведённой.

Линтинг и `mkdocs build --strict` дополняют этот список, но не проверяют удобство чтения экранным диктором, качество описаний или видимость фокуса. Доступность всего сайта требует отдельной оценки содержания и поведения темы.
