# Проверка и поддержка

## Автоматические проверки

**Q-01. Обязательно:** перед PR выполните из корня репозитория в активном окружении:

```bash
python -m pymarkdown --config .pymarkdown.json scan --recurse README.md CONTRIBUTING.md docs
mkdocs build --strict
```

Первый шаг проверяет структуру Markdown. Второй собирает сайт и отклоняет предупреждения, включая отсутствующие внутренние страницы и якоря. CI запускает эти же команды на push и PR. Успех линтера не доказывает отсутствие фактических ошибок, не проверяет внешние URL и не заменяет ручное ревью.

## Ручной контроль

**Q-02. Обязательно:** автор и рецензент проверяют следующее.

- Читатель и результат документа определены.
- Факты соответствуют закреплённой версии исходников.
- Термины совпадают со словарём, статусы — с кодом.
- У команд есть требования, рабочая папка и проверка результата.
- Нет секретов и персональных данных.
- Ссылки, изображения и таблицы понятны в собранном сайте.
- Ограничения MVP и непроведённые проверки названы прямо.
- Новая страница включена в навигацию.

## Публикация и изменения

**Q-03. Обязательно:** публикация выполняется только для `main` после успешного задания `check`. PR запускает проверки без публикации. Workflow загружает собранный каталог `site/` как артефакт Pages, а отдельное задание `deploy` публикует его с разрешениями `pages: write` и `id-token: write`.

После публикации откройте главную страницу, страницу примера и поиск. Проверьте статус deployment в Actions. Не считайте зелёную сборку подтверждением доступности публичного адреса.

Изменения проходят [процесс CONTRIBUTING](https://github.com/MarkovFedor/style-guide-project/blob/main/CONTRIBUTING.md). Отдельный PR доступности остаётся открытым до реального одобрения другого студента. Дата пересмотра и владелец указаны на главной странице.
