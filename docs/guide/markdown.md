# Markdown и иллюстрации

## Заголовки и списки

**M-01. Обязательно:** один заголовок первого уровня на страницу; уровни не пропускайте. Заголовок описывает содержание, без точки в конце. Перед списком, таблицей и блоком кода оставляйте пустую строку.

**M-02. Обязательно:** последовательность действий оформляйте нумерованным списком, независимые пункты — маркерами `-`. Команды оформляйте отдельными блоками с языком `bash`, данные — `json`, фрагменты Python — `python`.

Проверка: `python -m pymarkdown --config .pymarkdown.json scan --recurse README.md CONTRIBUTING.md docs`. Проверка длины строки отключена: адреса, таблицы и русский текст не разбиваются механически; читабельность оценивает рецензент. Остальные правила линтера действуют.

## Код и таблицы

**M-03. Обязательно:** пути, команды, параметры и значения API выделяйте обратными кавычками. Элементы интерфейса — полужирным. Не добавляйте приглашение `$` внутрь копируемой команды.

Пример: откройте **Settings → Pages**, выберите `GitHub Actions`.

Таблица должна иметь строку заголовков. Длинную последовательность действий помещайте в список, а не в одну ячейку.

## Ссылки и изображения

**M-04. Обязательно:** внутренние ссылки ведут на существующие `.md`-страницы относительно текущего файла; внешние ссылки имеют понятное название. Проверяйте внутренние цели и якоря строгой сборкой, внешние адреса — вручную.

Плохо: «подробнее здесь». Хорошо: «[правила проверки](quality.md)».

**M-05. Обязательно:** иллюстрация сопровождается содержательной подписью и текстовым объяснением смысла. Изображения храните в `docs/assets/`, имена — латиницей в `kebab-case` без пробелов. Обезличивайте персональные данные и секреты.

Плохо: `![alt text](diagram.png)`. Хорошо: `![Связи API, клиента ресторана и PostgreSQL](../assets/architecture.png)` — пример синтаксиса; файл создаётся вместе с иллюстрацией.

Проверка: просмотр страницы и соответствие подписи содержанию. Наличие подписи само по себе не доказывает доступность всей страницы.
