# Принципы и область применения

## Читатель и задача

**P-01. Обязательно:** в начале документа укажите, кому он нужен и какую задачу решает. Разработчик запускает сервис, интегратор вызывает API, рецензент проверяет архитектуру. Не смешивайте эти задачи без отдельных разделов.

Плохо: «Документация проекта». Хорошо: «Запуск backend локально для разработчика».

Проверка: рецензент может назвать читателя и ожидаемый результат после первого абзаца.

## Приоритет фактов

**P-02. Обязательно:** факты сверяйте с кодом конкретной версии. Указывайте коммит источника. При противоречии README и реализации фиксируйте расхождение, а не скрывайте его редактурой.

Пример: в README перечислены пять статусов обработки, но `OrderService.update_order_status` допускает также `pending` и `cancelled`.

Проверка: ссылки на исходники и версия в [источниках](../sources.md).

## Границы MVP

**P-03. Обязательно:** отделяйте реализованное поведение от планов. Не обещайте авторизацию, интеграцию оплаты, проверку всех переходов статусов или изоляцию ресторанов без подтверждения кодом.

Пример: параметр `restaurant_id` есть в пути обновления статуса, но обработчик передаёт константу `RESTAURANT_ID = 1`.

Проверка: для каждой заявленной возможности найдите реализацию; ограничения перечислите рядом с инструкцией.

## Уровни требований

«Обязательно» — условие принятия документа. «Рекомендуется» — правило, от которого можно отступить с обоснованием в PR. Пример иллюстрирует правило, но не заменяет контракт API. Формат правила: идентификатор → требование → пример → проверка.

Приоритет: фактический контракт версии → обязательные правила → рекомендации → примеры. Ошибки продукта отмечайте явно и предлагайте отдельное исправление кода.
