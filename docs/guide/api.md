# Команды и API

## Воспроизводимость

**C-01. Обязательно:** перед командами указывайте требования, рабочую папку и переменные окружения. После — наблюдаемый результат. Команды берите из кода, `Makefile` и конфигурации выбранной версии.

Пример: `make local_test` существует, а написанное в исходном README `make local-test` не соответствует `Makefile`.

**C-02. Обязательно:** отделяйте проверенные команды от примеров, не запущенных автором. Не включайте действующие пароли, токены и реальные адреса клиентов. Учебный пароль явно помечайте и используйте только для локальной среды.

Проверка: другой участник понимает, где выполнять команду и какие параметры заменить.

## Контракт API

**C-03. Обязательно:** для операции укажите метод, полный путь с префиксом, обязательные и необязательные поля, пример запроса, ожидаемый ответ и ошибки. Отмечайте побочные эффекты изменяющих запросов.

Пример: [обновление статуса заказа](../examples/order-status.md). Оно изменяет заказ и добавляет запись истории; для практики нужен тестовый заказ.

**C-04. Обязательно:** не выводите ограничения из одного названия метода. Проверяйте маршрутизатор, схему и сервис вместе. Если поведение отличается от ожидаемого, укажите фактическое ограничение рядом с примером.

Пример: `status` в `OrderStatusUpdate` — строка, а допустимые значения проверяет сервис. Сервис проверяет принадлежность заказа переданному ему ресторану, но endpoint передаёт константу `1` вместо параметра пути. Нельзя утверждать, что произвольный ресторан надёжно изолирован этим путём.

Проверка: ручное сопоставление запроса и ответа с исходниками. Линтер не проверяет истинность API-контракта.
