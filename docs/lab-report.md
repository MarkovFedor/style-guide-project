# Лабораторная работа 3: Docs as Code

Тема: разработка стайлгайда на разработку и оформление документации. Цель: пройти цикл от правил и примеров до версионирования, автоматической проверки и публикации сайта.

## 1. Изучение теории и примеров

Стайлгайд — набор согласованных правил для авторов и рецензентов: он задаёт терминологию, тон, структуру и оформление. Полезное правило должно быть проверяемым и объяснять действие автора на примере. Его поддерживают вместе с документацией: меняют через ветки, обсуждают в PR, проверяют в CI.

Изучены [Google style guide](https://developers.google.com/style/highlights), [Diátaxis](https://diataxis.fr/) и [пример Travel Buddy Finder](https://xsini.github.io/style-guide-project/). Из Google взяты принципы ясного действия и оформления кода; из Diátaxis — выбор структуры по потребности читателя; из примера — явные границы прототипа, словарь и апробация. Для backend дополнительно нужны точные пути API, переменные среды и предупреждения о фактических упрощениях реализации.

Презентация лабораторной отсутствует, поэтому её изучение не подтверждается. Полный список и границы исследования приведены в [источниках](sources.md).

## 2. Ответы на вопросы

### 2.1. Нужны ли стайлгайды всегда

Стайлгайд полезен, когда документы пишут несколько авторов, меняется команда или продукт, повторяются разночтения терминов. Он уменьшает время редакторских споров и делает критерии ревью явными. Например, единое различение `status` заказа и `payment_status` оплаты предотвращает ошибочные описания API.

Большой отдельный стайлгайд нужен не всегда. Для одноразовой заметки одного автора достаточно короткого чек-листа. Если стоимость поддержания правил превышает пользу, объём следует сократить. Для нашего проекта повторяются README, инструкции и справочники, поэтому небольшой версионируемый набор правил оправдан.

### 2.2. Как использовать при разработке документации

До написания автор выбирает читателя и шаблон; во время работы сверяет термины и оформляет команды; перед PR проходит чек-лист. Рецензент ссылается на идентификатор правила вместо субъективного «мне так нравится».

Примеры: C-01 требует указать рабочую папку и переменные среды для Docker Compose; T-02 не позволяет заменить `accepted` русской строкой в JSON; P-03 запрещает обещать реализованную изоляцию ресторанов без подтверждения кодом. Применение показано в [двух примерах](examples/validation.md).

### 2.3. Как использовать искусственный интеллект

ИИ может сгруппировать повторяющиеся ошибки, предложить структуру, варианты формулировок и пары «до/после», найти несогласованные термины и подготовить черновик чек-листа. Ему нужно дать область применения, читателя, исходники и обязательные ограничения.

Результат проверяет человек: ИИ может придумать endpoint, неверно понять ограничения или назвать непроведённую проверку успешной. Не передавайте секреты; фиксируйте источники и отделяйте редактуру от проверки поведения. В этой работе ИИ использован для исследования исходников, подготовки правил, примеров и конфигурации; независимое студенческое ревью этим не заменено.

Объект — русскоязычная документация [mvp-delivery-backend](https://github.com/MarkovFedor/mvp-delivery-backend): README, запуск, описание REST API, архитектура и ограничения MVP доставки еды. ## 4. Разработка стайлгайда

### 4.1. Структура правил

Правила отвечают на вопросы: кто читатель; какой факт подтверждён кодом; как называть сущности; как писать инструкции; как оформлять Markdown; что обязательно для API; как проверять и обновлять документацию. Каждое правило имеет идентификатор, обязательность, требование, пример и способ проверки.

### 4.2. Написанные правила

- P-01–P-03: читатель, версия источника и границы MVP.
- L-01–L-05: тон, действия, типографика, числа и сокращения.
- T-01–T-02: словарь и статусы заказа.
- S-01–S-03: типы документов, шаблон инструкции и формат правила.
- M-01–M-05: заголовки, списки, код, ссылки и изображения.
- C-01–C-04: воспроизводимость команд, секреты, контракт и ограничения API.
- Q-01–Q-03: автоматическая и ручная проверка, публикация.

### 4.3. Структура руководства

Главная → принципы → язык → терминология → структура → Markdown → команды и API → качество. Отдельно размещены примеры, протокол апробации, отчёт и источники. Порядок совпадает с `nav` в `mkdocs.yml`.

### 4.4. Фиксация правил

Правила сохранены в `docs/guide/`, исходники — Markdown в Git. Начните с [принципов](guide/principles.md). Владелец, версия и дата указаны на главной странице; порядок изменения — в `CONTRIBUTING.md`. Новый раздел доступности подготовлен отдельным PR, поэтому до его одобрения он не входит в опубликованную версию `main`.

## 11. Ветка и Pull Request

Для доступности используется ветка `docs/accessibility`: отдельная страница с правилами и пункт навигации. PR предназначен для настоящего ревью другим студентом. Автоматические проверки не заменяют approval. До реального одобрения PR не сливается, а независимое ревью и слияние остаются незавершёнными этапами.

Сохранённый исходный текст обрывается на «11.4 Сдела». Неизвестные дальнейшие требования не восстановлены догадкой. Для закрытия лабораторной полностью нужны реальный рецензент и, при необходимости, оставшаяся часть задания.
